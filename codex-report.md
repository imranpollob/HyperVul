# Codex Report: Divergent HyperVul Implementations and Restart Plan

Date: 2026-07-01

## Scope

This review is based on the code and generated JSON/CSV artifacts in this repository, not on the project Markdown narrative. Markdown files were treated as secondary evidence only when they were generated by scripts. The core finding is that HyperVul is not one stable system in this checkout. It is several partially overlapping modeling attempts that reuse names such as "hyperedge", "hypergraph", "fair baseline", and "ablation" for different data units, different training targets, and different baseline definitions.

## Executive Judgment

The project failed to produce a defensible "HyperVul beats baselines" result because the data, model unit, label unit, and baseline construction changed across attempts. Performance is not merely low; the comparison protocol is unstable. In one version HyperVul is a flat interaction classifier over function/state/callee members. In another it is a contract-scoped incidence hypergraph. In the newer fair-eval code, RQ1 baselines intentionally avoid HyperVul hyperedges, while RQ2 baselines receive HyperVul candidate hyperedges. Those are valid questions separately, but they cannot be mixed into one superiority claim.

The best current results are clustered and fragile. From generated JSON summaries:

| Experiment family | Best-looking row | Precision | Recall | F1 | F2 | PR-AUC |
|---|---:|---:|---:|---:|---:|---:|
| RQ1 generic baselines | function-features-mlp | 17.31 +/- 1.16 | 67.80 +/- 3.90 | 27.53 +/- 1.33 | 42.70 +/- 1.38 | 33.43 +/- 0.88 |
| RQ2 representation ablation | hyperedge-nn | 17.65 +/- 1.48 | 59.02 +/- 6.05 | 27.08 +/- 1.76 | 39.97 +/- 2.37 | 26.45 +/- 2.96 |
| RQ3 HyperVul ablation | full/security | 17.35 +/- 1.93 | 70.24 +/- 8.07 | 27.62 +/- 2.17 | 43.12 +/- 1.74 | 20.42 +/- 1.53 |
| RQ3 HyperVul ablation | emb-only | 18.28 +/- 1.08 | 61.46 +/- 6.43 | 28.09 +/- 1.32 | 41.56 +/- 2.32 | 22.99 +/- 1.17 |

These numbers do not support a strong architectural superiority story. The "full" HyperVul variant does not clearly dominate embedding-only, and PR-AUC is especially weak in RQ3.

## Implemented Motifs Found in Code

### 1. Legacy Flat Hyperedge Classifier

Main code:

- `model/latest1/model.py`
- `model/latest1/train.py`
- `model/latest1/run_baselines.py`
- `scripts/build_iteration3_data.py`

Build:

- Data unit: one interaction item from `data/splits/*.json`.
- Member structure: `[function] + [state vars] + [external calls]`.
- Embeddings: SmartBERT/Web3Se-style 768-dimensional embeddings stored inside split records.
- Model: attention or sequence pooling over hyperedge members, then MLP binary classification.
- Later add-ons: asymmetric loss, supervised contrastive loss, hard-negative weighting, symbolic sidecars, localization head.
- Training data is expanded with fixed OpenZeppelin clean negatives and swept Aave clean negatives. See `model/latest1/train.py:230-341`.
- Thresholding targets high validation recall and then measures false positives on clean negative pools. See `model/latest1/train.py:320-430`.

How it is documented:

- The code labels this as "iteration-3", "Stage 3", "Stage 4", "SCL", "localization", and "symbolic node features".
- The documentation problem is that several changes are presented as architectural progress, but the code also changes the negative pools and thresholding regime. This makes it hard to attribute any performance change to the model itself.

Why it failed:

- It is mostly a bag/sequence encoder over already-compressed member embeddings. It does not truly model contract-wide vulnerability conditions.
- The function embedding likely dominates because it contains much of the source text, making state/callee structure secondary.
- Adding more clean negatives reduces false positives but also changes the data distribution. It is a data repair/hard-negative strategy, not an architecture proof.
- The validation objective optimizes threshold behavior under sparse positives; this can make recall look intentional while precision remains low.
- The model additions are not isolated cleanly enough. Sequence pooling, SCL, localization, symbolic features, ASL, and negative sampling are all mixed.

### 2. Contract-Scoped Hypergraph Representation Comparison

Main code:

- `scripts/build_hypergraph.py`
- `src/models/hypergraph_nn.py`
- `src/models/set_pool.py`
- `src/models/gnn_zoo.py`
- `model/latest1/run_representation_comparison.py`

Build:

- Data unit: a contract graph assembled from interaction items.
- Hyperedge: one interaction function plus accessed state variables and external callees.
- Shared nodes: state variables and callees are shared inside a contract so interaction edges can exchange context.
- Baselines: set-pool, pairwise-GCN clique expansion, pairwise-GAT clique expansion, and hypergraph message passing.
- The comparison claims only the representation changes. See `model/latest1/run_representation_comparison.py:1-11`.
- Pairwise edges are constructed as all directed member pairs per hyperedge. See `model/latest1/run_representation_comparison.py:93-135`.
- It still uses legacy split files plus sampled OZ/Aave negatives. See `model/latest1/run_representation_comparison.py:280-315`.

How it is documented:

- This is the clearest code-level attempt to test the actual hypergraph hypothesis.
- The documentation around it risks overstating the result because this is a separate system from the flat HyperVul classifier and from the fair-eval HyperVul model.

Why it failed:

- It still inherits weak labels and legacy augmented splits.
- It compares representations over candidate interactions, but not necessarily over a validated vulnerability discovery task.
- It may not have enough positive examples for higher-order structure to be learnable.
- Pairwise clique baselines and hypergraph message passing share many inputs, so the expected advantage depends on real multi-edge dependencies being present and labeled. The current dataset does not prove that strongly.
- Threshold selection again targets recall, which can hide poor ranking quality.

### 3. Newer `hypervul_fair_eval` Evaluation Stack

Main code:

- `hypervul_fair_eval/src/fair_eval/data/load_existing.py`
- `hypervul_fair_eval/src/fair_eval/builders/*.py`
- `hypervul_fair_eval/src/fair_eval/models/*.py`
- `hypervul_fair_eval/scripts/rq1_run_generic_baselines.py`
- `hypervul_fair_eval/scripts/rq2_run_representation_ablation.py`
- `hypervul_fair_eval/scripts/rq3_run_hypervul_ablation.py`

Build:

- Loads canonical contract graphs from `data/contract_graphs` by default unless `HYPERVUL_GRAPH_DIR` is set.
- RQ1 builds generic views: function examples, sequence examples, callgraph views, pairwise graph views. It explicitly does not use HyperVul hyperedges. See `hypervul_fair_eval/scripts/rq1_run_generic_baselines.py:1-12` and `:80-171`.
- RQ2 builds HyperVul candidate hyperedges and gives all representation models the same candidates. See `hypervul_fair_eval/scripts/rq2_run_representation_ablation.py:1-6` and `:55-91`.
- RQ3 ablates the HyperVul model over embedding-only, security/symbolic, full, no-localize, and no-contrastive variants.

How it is documented:

- The code is much cleaner than the legacy scripts. It separates RQ1, RQ2, and RQ3.
- The documentation weakness is conceptual: RQ1 and RQ2 define "fair" differently. RQ1 baselines do not get HyperVul candidate hyperedges; RQ2 baselines do. These answer different questions and should not be merged into one table without explanation.

Why it failed:

- The default loader still points at `data/contract_graphs`, not the cleaner `data/contract_graphs_clean`, unless an environment variable overrides it.
- The model called "full" is still a candidate-interaction classifier with sequence pooling and localization, not the same contract-scoped hypergraph as motif 2.
- Results do not show a decisive full-model win. RQ3 `emb-only` has higher mean F1 and PR-AUC than `full/security` in the stored summary.
- The ablation is partly confounded: `security` and `full` appear identical in the stored RQ3 summary, which suggests either the variants are not differentiated enough or the summary is not proving the claimed components.

Main code:

- `scripts/build_clean_graph_dataset.py`
- `scripts/run_phase0d_clean_baselines.py`

- `scripts/run_phase1c_label_cleanup.py`
- `scripts/run_phase1d_contrastive_reentrancy.py`

Build:

- These scripts are attempts to repair the core problem: leakage, duplicate source, weak labels, wrong scope, lack of provenance, and false positives.
- `scripts/build_clean_graph_dataset.py` explicitly creates `data/contract_graphs_clean`, quarantine files, scope views, and embedded provenance without overwriting the original graph dataset. See `scripts/build_clean_graph_dataset.py:1-16`.
- Phase 0E changes the task to native contract-level MIL while keeping the existing interaction encoder.
- Phase 1A mines safety/context features and hard negatives.
- Phase 1B creates a risk-vs-safety architecture.
- Phase 1D introduces manual acceptance and contrastive reentrancy training.

How it is documented:

- This family is documented by many reports under `reports/`, but the reports should be treated as outputs from unstable experiments, not as the project truth.
- The code itself shows a sequence of rescue attempts after realizing the earlier data and label story was not adequate.

Why it failed:

- These scripts are improvements, but they are layered on top of a shaky existing dataset instead of resetting the dataset contract.
- They introduce more variants before locking down one canonical task.
- They generate many artifacts, making it easy to select favorable tables from incompatible experiments.
- The clean graph work is not consistently adopted by all runners.

## Baseline Construction Is Inconsistent

The project uses at least four baseline meanings:

1. Legacy ablations: remove state or callee members, or aggregate contract embeddings in `model/latest1/run_baselines.py`.
2. Heuristic/rule baselines: rule detectors in `experiments/run_baselines.py`.
3. Generic ML baselines: function MLP, sequence, callgraph GNN, pairwise graph in `hypervul_fair_eval/scripts/rq1_run_generic_baselines.py`.
4. Same-candidate representation baselines: set-pool, pairwise clique GNNs, hyperedge NN in `hypervul_fair_eval/scripts/rq2_run_representation_ablation.py`.

All four can be useful, but they cannot be presented as one baseline ladder. A fair paper table needs one fixed question per table:

- Generic detector question: Does HyperVul beat strong detectors that do not receive HyperVul candidate hyperedges?
- Representation question: Given the same candidate interactions, does hypergraph encoding beat set and pairwise reductions?
- Component question: Within HyperVul, which component actually helps?
- Tool question: How does the model compare to Slither/Mythril-style analyzers on the same evidence-backed contracts?

## Why the Divergent Versions Failed

Primary issues:

- No single canonical task. The code alternates among interaction classification, contract classification, clean-negative false-positive suppression, localization, and representation ablation.
- No single canonical dataset. Runners use `data/splits`, `data/splits_clean`, `data/contract_graphs`, `data/contract_graphs_clean`, and `data/contract_graphs_reentrancy_clean_v1`.
- Labels are not consistently evidence-backed. Later scripts try to repair provenance and labels, which implies the earlier experiments were not reliable.
- Positive support is too small for high-confidence claims, especially in reentrancy-only evaluation.
- HyperVul architecture is not stable. "HyperVul" can mean set/sequence pooling, contract hypergraph message passing, MIL, risk-safety gating, or fair-eval candidate scoring.
- Baselines are moving targets. The code changes both the model and the comparison data/views.
- Threshold policy hides ranking weakness. Many scripts optimize validation thresholds for target recall; PR-AUC and precision remain weak.
- Generated Markdown overstates coherence. The code shows experimental branching, not one mature system.
- Clean data work exists but is not the default path everywhere.
- The implementation tries to win by add-ons before proving the base representation is learnable.

## Clean Restart Plan

### Phase 0: Freeze the Research Question

Start with one vulnerability family, preferably reentrancy only. Do not mix unchecked low-level calls, delegatecall, front-running, and generic interaction bugs until the first scope is stable.

Define three targets up front:

- Contract-level detection: whether a contract contains an exploitable vulnerability.
- Interaction-level localization: which interaction candidate is responsible.
- Evidence-level explanation: which function/state/callee/guard tuple supports the label.

### Phase 1: Data Collection

Use raw sources only:

- DAppSCAN raw Solidity projects and audit metadata.
- FORGE-Curated vulnerable findings and affected files.
- Clean audited contracts with explicit no-finding status.
- Fixed versions of vulnerable contracts when available.
- Optional external holdouts: OpenZeppelin, Aave, MakerDAO, Bancor, Liquity, but only as frozen holdout or clean-negative pools, not mixed ad hoc into training.

For every contract, store:

- Raw source path and commit/version.
- Compiler version.
- Contract name and file hash.
- Normalized contract hash.
- Function source hash.
- Audit finding id and evidence pointer for positives.
- Reason for negative label.
- Scope label and confidence.

### Phase 2: Labeling Protocol

Use four labels, not binary at first:

- `positive`: audit-backed exploitable vulnerability with function/evidence mapping.
- `negative`: audited clean or fixed-safe evidence.
- `wrong_scope`: finding exists but not the target vulnerability family.
- `ambiguous`: insufficient evidence; never train or test on this.

Rules:

- A positive interaction must have an evidence pointer to the finding and the source span.
- A negative interaction must have a negative rationale, not simply "no finding matched".
- Manual review decisions must be stored as data, not embedded in report prose.
- Test labels must be frozen before model development.

### Phase 3: Split Discipline

Split by leakage components, not rows:

- Same project family stays in one split.
- Same normalized contract hash stays in one split.
- Same function hash stays in one split.
- Same source file lineage stays in one split.
- Fixed/vulnerable pairs stay in the same split unless the experiment explicitly studies repair transfer.

Create one canonical graph directory, for example:

`data/hypervul_v2_reentrancy/{train,val,test,quarantine}.json`

All scripts must load this by default. No runner should silently fall back to older splits.

### Phase 4: Absolute Hyperstructure to Follow

Use one contract-level heterogeneous hypergraph schema:

Node types:

- `contract`
- `function`
- `state_variable`
- `external_call`
- `callee_contract`
- `modifier_or_guard`
- `role_or_actor`
- `asset_or_token`
- `finding_evidence`

Hyperedge types:

- `interaction`: function, touched state variables, external calls, callees, caller/role, asset.
- `state_transition`: function, state variables read/written, order information.
- `external_effect`: function, external call, callee contract, method, value transfer.
- `guard_relation`: function, modifier/require/assert/nonReentrant/access-control evidence.
- `finding_alignment`: evidence span, function, contract, vulnerability scope.
- `repair_pair`: vulnerable function and fixed function when both exist.

Labels:

- Contract label on `contract`.
- Interaction label on `interaction` hyperedges.
- Optional tuple label on `(function, state_variable, external_call)` only when evidence supports it.

This schema keeps the HyperVul claim precise: vulnerability conditions are n-ary relations among function behavior, state, external effects, and safety guards.

### Phase 5: Model Creation

Build the model in layers and stop when a layer does not help:

1. Text/code encoder: frozen code embeddings first; fine-tuning only after the graph task is stable.
2. Symbolic feature encoder: call type, return checked, state update before/after call, nonReentrant, access control, callee trust, value transfer.
3. Hypergraph encoder: node-to-hyperedge and hyperedge-to-node message passing over the canonical schema.
4. Contract MIL head: aggregate interaction scores into contract-level detection.
5. Localization head: rank interaction hyperedges and function-state-callee tuples.
6. Calibration head: choose thresholds on validation only; report PR-AUC independently.

Do not add contrastive learning, hard-negative mining, or augmentation until this base stack has stable learning curves and beats simple baselines.

### Phase 6: Baseline Comparison

Use one dataset, one split, one threshold protocol, one metric package.

Baselines:

- Rule tools: Slither/Mythril-style detectors, with runnable harnesses and failure logs.
- Function MLP: function embedding only.
- Function+symbolic MLP: function embedding plus symbolic safety/risk features.
- Sequence model: ordered function/member sequence.
- Callgraph GNN: conventional graph over functions and calls.
- Pairwise clique GNN: same interaction candidates reduced to pairwise edges.
- Set-pool hyperedge model: same candidates, no structure.
- Hypergraph model: the proposed model.

Report:

- Contract-level: Precision, Recall, F1, F2, PR-AUC, ROC-AUC.
- Localization: Top-1, Top-3, MRR, Recall@3.
- Robustness: seed mean/std, bootstrap CI, per-project holdout.
- Error analysis: top false positives and false negatives with source evidence.

### Phase 7: Acceptance Criteria

Do not write paper-facing claims until all are true:

- Dataset audit passes leakage checks.
- Every positive test example has source evidence.
- Every negative test example has a negative rationale.
- Hypergraph beats pairwise and set-pool on the same candidate set with confidence intervals.
- Hypergraph or HyperVul full beats generic baselines on contract-level PR-AUC and F2, not only thresholded recall.
- Localization identifies evidence-bearing interactions better than baseline ranking.
- External holdout false-positive behavior is reported, even if it is bad.

## Recommended Immediate Repository Actions

1. Freeze old experiment families under an `archive/` or `legacy/` namespace.
2. Make `data/contract_graphs_clean` or a new `data/hypervul_v2_reentrancy` the only default dataset.
3. Delete or quarantine Markdown reports that are not generated by a current script.
4. Add one `configs/experiment_v2.yaml` that specifies graph directory, scope, seeds, models, thresholds, and metrics.
5. Rewrite runners so RQ1, RQ2, and RQ3 all accept the same config and output one machine-readable result schema.
6. Add a preflight audit command that blocks training if split leakage, missing provenance, or ambiguous labels are present.
7. Rebuild the paper tables only after the canonical pipeline runs end to end.

## Bottom Line

The project should restart from data and labeling, not from model tuning. The most defensible HyperVul system is a contract-level heterogeneous hypergraph with interaction hyperedges, evidence-backed labels, leakage-safe splits, and baselines run on the same frozen dataset. The current repository contains useful pieces, especially the clean graph rebuild and fair-eval scaffolding, but the divergent modeling motifs must not be merged into a single performance story.
